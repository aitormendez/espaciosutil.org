## Criterios de aceptación

SSH por clave, acceso administrativo probado antes de cerrar root, firewall, servicios con inicio automático, HTTPS válido, WordPress con base de datos propia y cuenta sintética, aislamiento de correo e integraciones, y pruebas de que el aislamiento sólo se aplica a staging. No se copian alumnos, pedidos, suscripciones ni claves de integraciones reales.

## Aislamiento inicial

El entorno desactiva cron de WordPress y el cron de Trellis, Matomo y las credenciales SMTP/Bunny/YouTube heredadas. El correo del sistema apunta a un puerto local sin servidor. Un mu-plugin devuelve fallo en `wp_mail`, bloquea toda petición de la API HTTP de WordPress antes del transporte y desactiva la sincronización Listmonk y la consulta automática de pedidos Stripe. También bloquea actualizaciones y llamadas de comprobación de WordPress; las dependencias se instalan mediante el despliegue.

Este bloqueo cubre las APIs de WordPress; no es un firewall de salida para código que use cURL o sockets directamente. No instalar claves reales ni importar opciones de producción. La futura prueba de Bunny necesitará una excepción explícita y restringida, con pruebas de autorización. El acceso público al host no equivale a autorización sobre las lecciones.

## Compatibilidad y capacidad

MariaDB usa el paquete de Ubuntu en staging, conservando por defecto el repositorio externo para los demás entornos. PHP 8.4 tiene un máximo de tres procesos FPM y 256 MiB por proceso; se configura 1 GiB de swap. Los assets se compilan en el Mac. No es una prueba de carga.

Se corrigen los plugins de Trellis para Python 3.12/Ansible 2.18 y el hook de bloques: instalación y compilación son comandos separados y los assets se copian al release. El workflow manual de staging exige una clave de host conocida; no acepta ciegamente el resultado de `ssh-keyscan`.

## Operación y reversión

Usar Trellis desde la rama que contiene el inventario nuevo y limitar siempre el primer aprovisionamiento a `138.68.135.185`. El archivo de claves de host usado inicialmente es `/private/tmp/espacio-sutil-staging-known-hosts`; conservar su entrada verificada en el gestor habitual y en el secreto GitHub del entorno staging antes de automatizar despliegues. No restaurar el DNS a la IP retirada como rollback. Un release fallido se revierte al anterior del mismo staging; si aún no existe, mantener el sitio fuera de servicio mientras se corrige.

Los backups diarios están seleccionados en DigitalOcean. Su existencia y una restauración de prueba son verificaciones distintas del aprovisionamiento.
